# Identifier coverage baseline

Measured 13 September 2026. Re-measured 20 September 2026.
Reproduce with `python3 scripts/coverage.py`. Check without rewriting with
`python3 scripts/coverage.py --check`.

**Correction, 20 September 2026.** The 13 September run was produced by a script that
was never committed, so its counting rules for two elements could not be recovered.
`scripts/coverage.py` now states every rule in its own docstring and is the source of
these numbers. Eight of the ten figures reproduce exactly. Two do not, and both moved
down: supplier from 702 to 260, license from 3,674 to 1,057. The superseded file is
kept at `docs/coverage-baseline.superseded-2026-09-13.json`. Operating rule 8: take the
number from the thing that runs.

No published figure exists for what share of SBOM components carry a usable identifier.
The one public attempt to build the underlying PURL to CPE mapping is documented by its
authors as having failed. This is the first measurement StratifyPro publishes, and it
is the first data point of `bench/identity`.

## Corpus

21 real published SBOMs, 5,088 components, drawn from the Chainguard `bom-shelter`
in-the-wild and in-the-lab collections. Eight CycloneDX (1.2 to 1.4), thirteen SPDX
(2.2). Selected by spreading across component count so the set is neither all tiny nor
all huge, plus three container SBOMs generated by three different tools (syft, trivy,
tern) on comparable inputs so tool disagreement is visible inside the corpus.
Provenance and SHA-256 for every file: `fixtures/corpus/provenance.json`.

## What these numbers mean

**CPE coverage is 40.9 percent, and that is the finding that matters.** Fewer than half
of all components can be looked up by CPE at all. Combined with NIST's 15 April 2026
change, which limits CPE enrichment to KEV entries, federal software and EO 14028
critical software, CPE-first matching cannot work for the majority of components.
This is the measured basis for non-negotiable 5 in the spec: PURL first, CPE second.

**Supplier is 5.1 percent.** The 2026 CISA elements renamed this Component Producer
and treat it as a minimum element. Nineteen components in twenty do not have it. A published
study across 10,000 repositories found zero percent coverage for primary and top-level
components specifically; this corpus is a little better because it counts transitive
components too, where package managers supply the field automatically.

**Zero files out of 21 declare incompleteness.** Not one uses `compositions` to say its
dependency graph is partial. Eight of 21 have no dependency relationships at all. So in
eight cases a reader cannot distinguish "this software has no dependencies" from "this
tool did not record any", and in zero cases did an author say which it was. This is
what CISA's Explicitly Identifying Unknown Information practice exists to fix, and
nobody is doing it.

**Three files have zero PURL coverage**, including a 175-component container SBOM from
one generator. Same class of input, same year, and a 99 percent gap between the best
and worst tool.

## Honest limitations

**This corpus is kinder than the population.** It skews toward Go binaries and
container images produced by well-maintained generators. Published academic measurement
finds far worse results in Python and C, with component-detection F1 as low as 13.2
percent for one common tool on Python and license accuracy as low as 1.7 percent. The
94.8 percent PURL figure above should not be read as the state of SBOMs generally. It
is the state of *this* corpus, and the corpus is stated so anyone can disagree with it.

**Presence is not correctness.** Every figure here counts whether a field is populated.
None of them checks whether the value is right. A PURL that points at the wrong package
counts as coverage in this measurement and is worse than no PURL in practice. Measuring
correctness is what `bench/identity` is for, and it is a harder problem.

**One format, one version, mostly.** All thirteen SPDX files are 2.2. No SPDX 3.0 file
appeared in the source collection. Re-run this when 3.0 files are available in the wild.

## Method

The authority is `scripts/coverage.py`. This section restates what that file does; if
the two ever disagree, the script is right and this text is wrong.

1. Parse each file. CycloneDX components are walked recursively so nested components
   are counted. SPDX packages are taken as the flat list.
2. `NOASSERTION` and `NONE` never count as a value, in either format.
3. **PURL:** CycloneDX `purl`, SPDX an `externalRefs` entry of type `purl`. **CPE:**
   CycloneDX `cpe`, SPDX an `externalRefs` entry whose type starts with `cpe`.
   CycloneDX `externalReferences` is not consulted, because no component in this corpus
   carries a PURL or a CPE only there.
4. **Supplier** means the entity that produced the component: CycloneDX `supplier.name`
   or `publisher`, SPDX `supplier` or `originator`. CycloneDX `author` is deliberately
   excluded, because it names whoever wrote the SBOM entry rather than whoever produced
   the component. **That single exclusion is what moved this figure from 702 to 260.**
5. **License** means a license actually asserted. A CycloneDX `licenses` array counts
   only if some entry carries an `expression`, a license `id` or a license `name`. An
   entry carrying nothing but a `url` does not count, and neither does an `id` of
   `NOASSERTION`. 139 components in this corpus fail exactly that test.
6. Document-level checks look for `dependencies` or `relationships`, and for
   `compositions`.
7. Totals are component-weighted, not file-weighted, so large files count for more.
   Per-file figures are in `docs/coverage-baseline.json`.

Anyone can re-run this against their own corpus and get a different answer. The method
above, and the script, are the whole of it.
